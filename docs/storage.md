# Packet artifact storage

`paprika__Storage__Provider` is `filesystem` (default) or `azureblob`. Azure requires `paprika__Storage__Container` (a pre-created, private container) and **one** of `paprika__Storage__ServiceUri` (HTTPS Blob service URL, system-assigned managed identity) or `paprika__Storage__ConnectionString` (secret). For Azurite use a connection string and `localhost`, a loopback IP, or the Docker service name `azurite`.

Blob keys start with `packets/<packetId>/originals/` or `packets/<packetId>/exports/<revision>/`. Display names and submitted document IDs are never used as storage paths.

For an Azure smoke test use `paprika__Storage__Provider=AzureBlob` (case-insensitive). The original is `packets/<packetId>/originals/<sourceId>.<ext>`; its recoverable working copy is `<DataDirectory>/<packetId>/<sourceId>.<ext>`. The approved bundle is `packets/<packetId>/exports/<revision>/packet-<sha256>.zip` (an additional evidence digest is included for platform workflows). Each PDF is `.../document-001-<sha256>.pdf`, etc. Requesting the bundle also materializes every PDF. The API never redirects a client to the container.

## Operating contract

- Keep `paprika__DataDirectory` on a durable, private volume in **both** modes. SQLite holds packets, jobs, approved-export receipts and the storage location. Reviewed metadata, OCR, local work files, delivery receipts and other platform outputs can contain sensitive content regardless of byte-storage provider. Preserve single-instance access and protect the volume and backups with encryption and OS access controls.
- New intake publishes the validated source before committing the packet and job. This includes demo samples, folder imports and reprocessing. Filesystem originals retain the existing `<packetId>/<sourceId>.<ext>` layout. Azure downloads use the authoritative Blob. Processing tools may reuse a local hash-verified working file; after eviction they fetch and verify it before use. Never delete original files for filesystem or legacy sources. Legacy packets and revision snapshots have no provider marker; these still use their existing local originals.
- The first startup binds the data root to its selected provider and, for Blob, its service and container. Credentials can rotate. Changing these settings is **not** a migration mechanism; use a new data root for a new installation. No background migration or fallback occurs.
- Use a dedicated private container with anonymous access disabled at account level. Grant the application identity container-properties read and blob read/create permissions; the application does not need delete permission. Use TLS for Azure, restrict network access, protect connection strings with a secret store, and use managed identity where available. Blob creation is conditional; the application never overwrites an existing artifact. Account WORM/immutability policy and administrator access are separate controls.
- Approved downloads check the current approval and applicable release gates inside the same SQLite writer transaction that selects or creates the receipt. Stored bytes are checked against the receipt before serving. PDFs embedded in the canonical ZIP are exactly the individually downloadable bytes. Changed evidence on the same revision creates a separate immutable ZIP. Missing or corrupt authoritative bytes fail the request; restore them rather than deleting receipts. Delivery-specific snapshots (e.g. ZIPs containing a receipt or connector provenance) retain their own existing retention and storage rules.

## Archive and retention

Logical archive preserves originals, exports, jobs and history. Filesystem permanent purge, only when existing policy, authorization and dependency checks permit it, removes the packet directory (including every cached export) and its SQLite receipts. Azure permanent purge is **blocked**: ordinary Blob deletion cannot attest that versions, snapshots, soft-deleted bytes and legal holds have all been resolved. Use a separately reviewed account-level retention/erasure process. Do not configure automatic expiry or tier artifacts to an offline tier while packets or backups depend on them.

SQLite and object storage are separate durability domains. If interrupted between an immutable write and the SQLite commit, unreferenced objects or working files can remain. Retry the operation normally: uncommitted exports have content-addressed names and are never adopted without verifying their content. No automatic garbage collector removes bytes. To inventory remnants, stop all writers, take coordinated backups, compare packet/source IDs and export receipts in SQLite to the object inventory, and account for backups, delivery snapshots, retention policy and legal holds before operator removal.

## Backup and restore

**Filesystem:** stop all writers and use the [offline backup and restore scripts](recovery.md). The data tree includes original files, all immutable exports and their SQLite receipts.

**Azure Blob:** stop the application, retention tools and every other writer. Make a protected backup of **all** objects in the dedicated private container, preserving exact keys and bytes. Record object names, lengths and SHA-256 hashes in a private manifest, plus recovery point, account/service and container identity. With writers still stopped, run `scripts/backup.ps1 -DataDirectory <root> -OutputDirectory <new-location> -CoordinatedBlobBackup`. Keep both parts together; a cache, version history by itself, an empty container, or just a copy of `jobs.sqlite` is not a recovery point. The switch acknowledges the external backup; the script never contacts Azure.

To recover, stop all writers, restore the matching objects to the recorded service URI and private container, and verify their names, lengths and hashes against the protected manifest. Restore the local tree into a new directory using `scripts/restore.ps1 -BackupDirectory <backup> -DataDirectory <new-root> -CoordinatedBlobRestore`. Configure that root, the same provider/location, and valid credentials. Do not run the old and recovered installations concurrently. Verify an original download and approved ZIP/PDF hashes against the recovery point before reopening access. Retain the restored local tree even on Blob installations: it can include pre-upgrade originals, local delivery artifacts and platform outputs.
